# Phase 2: Boot Sequence (32-bit → 64-bit Long Mode)

> **Difficulty**: Intermediate  
> **Duration**: 45 minutes  
> **Learning Goals**: Understand Multiboot2, protected mode initialization, PAE setup, long mode activation, and kernel entry

## Overview

Your kernel doesn't start from CPU reset. A **bootloader** (GRUB in our case) initializes the CPU, loads your code, and hands control to your kernel. Understanding this handoff is **critical** to OS development.

This phase covers:

1. **Multiboot2 specification** – How GRUB identifies and validates your kernel
2. **Protected mode → long mode transition** – CPU state changes required
3. **Physical Address Extension (PAE)** – Enabling 36-bit addressing (prerequisite for 64-bit)
4. **4-level page table setup** – Building the paging hierarchy
5. **EFER.LME activation** – Switching on 64-bit mode
6. **64-bit kernel entry (kmain)** – Receiving control from bootloader
7. **Stack setup and CPU initialization** – Preparing the kernel environment

## 1. Multiboot2 Specification

### What is Multiboot2?

**Multiboot2** is a standardized specification (GNU GRUB) that allows any bootloader to load any kernel without hardcoding kernel-specific code. The bootloader:

1. Scans the first 32 KB of your kernel binary for the **Multiboot2 header**
2. Validates the magic number and checksum
3. Loads the kernel into memory
4. Places a pointer to a **Multiboot info structure** in a register
5. Jumps to the kernel's entry point with interrupts disabled

### Multiboot2 Header Structure

```c
// Multiboot2 header (must appear within first 32 KB of the binary)
typedef struct {
    uint32_t magic;           // 0xE85250D6 (Multiboot2 magic)
    uint32_t architecture;    // 0 = 32-bit i386, 4 = MIPS
    uint32_t header_length;   // Length of this header + tags
    uint32_t checksum;        // -(magic + architecture + header_length)
    
    // Tags follow (each tag: type, flags, size, data...)
    uint16_t tag_type;
    uint16_t tag_flags;
    uint32_t tag_size;
    // ... tag data ...
    
    // End tag (type=0, flags=0, size=8)
    uint16_t end_type;        // 0
    uint16_t end_flags;       // 0
    uint32_t end_size;        // 8
} multiboot2_header_t;
```

### Jarvis OS Multiboot2 Header

```assembly
; src/arch/x86_64/asm/loader.s
; =============================================================================
; Multiboot2 Header (must be 8-byte aligned, in first 32 KB of binary)
; =============================================================================
bits 32

section .multiboot2_header
align 8
.mb2_start:
    ; ┌─────────────────────────────────────────────────────────────────┐
    ; │ MULTIBOOT2 MAGIC HEADER (16 bytes)                              │
    ; └─────────────────────────────────────────────────────────────────┘
    dd 0xE85250D6                      ; Magic: Multiboot2 identifier
    dd 0                               ; Architecture: 0 = 32-bit protected mode
    dd (.mb2_end - .mb2_start)         ; Header length (from start to end tag)
    
    ; ┌─────────────────────────────────────────────────────────────────┐
    ; │ CHECKSUM (makes sum of all 4 DWORDs = 0)                        │
    ; │ This allows GRUB to validate the header isn't corrupted.        │
    ; │ Checksum = -(magic + architecture + header_length)             │
    ; └─────────────────────────────────────────────────────────────────┘
    dd -(0xE85250D6 + 0 + (.mb2_end - .mb2_start))\n    \n    ; ┌──────────────────────────────────────────────────────────────────┐\n    ; │ FRAMEBUFFER TAG (optional, but strongly recommended)            │\n    ; │ Tells GRUB we want graphics support. GRUB will provide a        │\n    ; │ framebuffer in the Multiboot info, allowing kernel to display  │\n    ; │ text/graphics without reinitializing the video hardware.        │\n    ; └──────────────────────────────────────────────────────────────────┘\n    align 8\n    dw 5        ; Tag type: 5 = framebuffer\n    dw 0        ; Flags: 0 = required (GRUB must provide framebuffer)\n    dd 20       ; Tag size: 8 (header) + 12 (data) = 20 bytes\n    dd 0        ; Preferred width (0 = no preference, GRUB chooses)\n    dd 0        ; Preferred height (0 = no preference)\n    dd 0        ; Preferred color depth (0 = any depth OK)\n\n    ; ┌──────────────────────────────────────────────────────────────────┐\n    ; │ END TAG (required, terminates tag list)                          │\n    ; └──────────────────────────────────────────────────────────────────┘\n    align 8\n    dw 0        ; Type: 0 = end tag\n    dw 0        ; Flags: 0\n    dd 8        ; Size: 8 bytes (just the header, no data)\n.mb2_end:\n```\n\n### Educational Breakdown: Multiboot2 Design\n\n**Why checksum?** GRUB checksums the header to detect corruption. The three values (magic + architecture + header_length) are chosen such that their sum equals zero—a simple but effective integrity check.\n\n**Why 8-byte alignment?** Tags must be aligned to support various data widths (e.g., 64-bit pointers). This simplifies parsing.\n\n**Why framebuffer tag?** Without this tag, GRUB doesn't provide video mode information. Your kernel would have to probe video hardware manually (complex). With the tag, GRUB initializes graphics and passes the framebuffer address to your kernel.\n\n---\n\n## 2. Multiboot Info Structure\n\nWhen GRUB boots your kernel, it passes a pointer to a **Multiboot info structure** containing critical data:\n\n```c\n// include/pmm.h\ntypedef struct {\n    uint32_t flags;              // Bit flags indicating which fields are valid\n    uint32_t mem_lower;          // Amount of lower memory (below 1 MB)\n    uint32_t mem_upper;          // Amount of upper memory (above 1 MB), in KB\n    uint32_t boot_device;        // Boot device number\n    uint32_t cmdline;            // Pointer to kernel command line string\n    uint32_t mods_count;         // Number of modules (e.g., ramdisk)\n    uint32_t mods_addr;          // Pointer to module list\n    // ... more fields ...\n    uint32_t mmap_length;        // Length of memory map\n    uint32_t mmap_addr;          // Pointer to memory map (array of entries)\n    uint32_t drives_length;      // Length of drive list\n    uint32_t drives_addr;        // Pointer to drive list\n    // ... Framebuffer info ...\n    uint64_t framebuffer_addr;   // Physical address of framebuffer\n    uint32_t framebuffer_width;  // Width in pixels\n    uint32_t framebuffer_height; // Height in pixels\n    uint32_t framebuffer_pitch;  // Bytes per scanline\n    uint8_t framebuffer_bpp;     // Bits per pixel\n    uint8_t framebuffer_type;    // 1=RGB, 2=indexed color\n} __attribute__((packed)) multiboot_info_t;\n\ntypedef struct {\n    uint32_t size;      // Size of this entry (4 + 4 + 8)\n    uint64_t addr;      // Base address of memory region\n    uint64_t len;       // Length of region\n    uint32_t type;      // 1=usable, 2=reserved, 3=ACPI reclaimable, 4=NVS\n} __attribute__((packed)) multiboot_mmap_entry_t;\n```\n\n**Key fields for kernel initialization**:\n- `mmap_addr + mmap_length` → Memory map (which RAM is available)\n- `framebuffer_addr, width, height` → Graphics output\n- `mods_addr, mods_count` → Loaded modules (like ramdisk)\n\n---\n\n## 3. The 32-bit Bootstrap\n\nWhen GRUB loads your kernel, the CPU is in **32-bit protected mode**. Your code must:\n1. Save Multiboot registers (before they're overwritten)\n2. Set up a temporary 32-bit stack\n3. Enable PAE (prerequisite for 64-bit)\n4. Build minimal 4-level page tables\n5. Activate long mode\n6. Jump to 64-bit code\n\n### Full Bootloader Assembly (loader.s)\n\n```assembly\n; =============================================================================\n; loader.s – x86_64 Jarvis OS Bootloader Entry Point\n; =============================================================================\n; GRUB boots us in 32-bit protected mode (CP0 = 1, long mode = 0)\n; Our task: transition to 64-bit long mode and call kmain(rdi=magic, rsi=mbi)\n; =============================================================================\n\nbits 32                    ; Assemble as 32-bit (GRUB's mode)\n\nglobal loader              ; Entry point symbol\nglobal gdt_flush           ; Export GDT loading function\nglobal idt_load            ; Export IDT loading function\nextern kmain               ; Kernel entry point (in C)\n\n; =============================================================================\n; MULTIBOOT2 HEADER (see Section 1)\n; =============================================================================\nsection .multiboot2_header\nalign 8\n.mb2_start:\n    dd 0xE85250D6\n    dd 0\n    dd (.mb2_end - .mb2_start)\n    dd -(0xE85250D6 + 0 + (.mb2_end - .mb2_start))\n    \n    align 8\n    dw 5        ; Framebuffer tag\n    dw 0\n    dd 20\n    dd 0\n    dd 0\n    dd 0\n    \n    align 8\n    dw 0        ; End tag\n    dw 0\n    dd 8\n.mb2_end:\n\n; =============================================================================\n; TEMPORARY 32-BIT GDT (used before we switch to 64-bit GDT in kernel.c)\n; =============================================================================\nsection .text\nalign 8\ngdt64:                      ; 32-bit GDT for bootstrapping\n    dq 0                     ; Null descriptor (required)\n.code: equ $ - gdt64         ; Code segment descriptor (offset = 0x08)\n    ; 64-bit code descriptor:\n    ; Bit 43 = DC (conforming, ignored for code)\n    ; Bit 44 = RW (readable, allows reads from code segment)\n    ; Bit 47 = P (present)\n    ; Bit 53 = L (long mode flag)\n    dq (1<<43) | (1<<44) | (1<<47) | (1<<53)\n    \n.data: equ $ - gdt64         ; Data segment descriptor (offset = 0x10)\n    ; 64-bit data descriptor:\n    ; Bit 44 = RW (writable)\n    ; Bit 47 = P (present)\n    ; Bit 41 = W (expansion direction)\n    dq (1<<44) | (1<<47) | (1<<41)\n\ngdt64_ptr:                   ; GDT pointer (for lgdt instruction)\n    dw $ - gdt64 - 1         ; Limit = size - 1\n    dd gdt64                 ; Base address (32-bit, fine before long mode)\n\n; =============================================================================\n; LOADER ENTRY POINT (called by GRUB)\n; =============================================================================\nloader:\n    cli                      ; Disable interrupts (bootloader may have left them on)\n    \n    ; ─────────────────────────────────────────────────────────────────────\n    ; STEP 1: Save Multiboot registers before they're overwritten\n    ; ─────────────────────────────────────────────────────────────────────\n    ; GRUB passes:\n    ;   EAX = magic number (0x36D76289 for Multiboot2, 0x2BADB002 for MB1)\n    ;   EBX = pointer to Multiboot info structure (physical address)\n    ; These will be overwritten by subsequent operations, so we save them.\n    \n    mov [saved_magic], eax   ; Store magic in .data section\n    mov [saved_mbi], ebx     ; Store MBI pointer in .data section\n    \n    ; ─────────────────────────────────────────────────────────────────────\n    ; STEP 2: Set up temporary 32-bit stack\n    ; ─────────────────────────────────────────────────────────────────────\n    ; Stack grows downward (toward lower addresses).\n    ; RSP/ESP must point to the top (highest address) of the stack.\n    mov esp, stack32_top     ; Stack range: [stack32_bottom, stack32_top)\n    \n    ; ─────────────────────────────────────────────────────────────────────\n    ; STEP 3: Enable PAE (Physical Address Extension)\n    ; ─────────────────────────────────────────────────────────────────────\n    ; PAE is a 32-bit extension that allows 36-bit physical addresses.\n    ; It's a prerequisite for 64-bit long mode (requires 4-level paging).\n    ; CR4.PAE = bit 5\n    \n    mov eax, cr4             ; Load CR4 (control register 4)\n    or  eax, 1 << 5          ; Set bit 5 (PAE bit)\n    mov cr4, eax             ; Write CR4 back\n    \n    ; ─────────────────────────────────────────────────────────────────────\n    ; STEP 4: Build minimal 4-level page tables for identity mapping\n    ; ─────────────────────────────────────────────────────────────────────\n    ; We'll use 2 MB huge pages (PS bit) for simplicity.\n    ; This requires 4 tables: PML4 → PDPT → PD → PT\n    ; \n    ; Layout:\n    ;   PML4[0] → PDPT (covers 0 – 512 GB)\n    ;   PDPT[0] → PD (covers 0 – 1 GB)\n    ;   PD: 2048 entries × 2 MB each = 4 GB\n    \n    ; Load PML4 address into CR3 (page table base register)\n    mov edi, pml4_table\n    mov cr3, edi\n    \n    ; Set up PML4[0] → PDPT\n    mov eax, pdpt_table\n    or  eax, 0x3             ; Set P (present, bit 0) and RW (writable, bit 1)\n    mov [pml4_table], eax    ; PML4[0] = PDPT address | flags\n    mov dword [pml4_table + 4], 0  ; Upper 32 bits of 64-bit entry = 0\n    \n    ; Set up PDPT[0] → PD\n    mov eax, pd_table\n    or  eax, 0x3\n    mov [pdpt_table], eax    ; PDPT[0] = PD address | flags\n    mov dword [pdpt_table + 4], 0\n    \n    ; Set up PDPT[1] → PD2 (covers 1 GB – 2 GB, for kernel later)\n    mov eax, pd_table2\n    or  eax, 0x3\n    mov [pdpt_table + 8], eax  ; PDPT[1] at offset 8 (next 8-byte entry)\n    mov dword [pdpt_table + 12], 0\n    \n    ; Set up PDPT[2] → PD3 (covers 2 GB – 3 GB)\n    mov eax, pd_table3\n    or  eax, 0x3\n    mov [pdpt_table + 16], eax\n    mov dword [pdpt_table + 20], 0\n    \n    ; Set up PDPT[3] → PD4 (covers 3 GB – 4 GB)\n    mov eax, pd_table4\n    or  eax, 0x3\n    mov [pdpt_table + 24], eax\n    mov dword [pdpt_table + 28], 0\n    \n    ; Fill PD tables with 2 MB huge pages\n    ; Each PD has 512 entries, covering 1 GB total (512 × 2 MB = 1 GB)\n    ; We need 4 PDs to cover 4 GB\n    mov ecx, 0                 ; Loop counter = 0\n    \n.fill_pd:\n    ; Calculate physical address: ecx * 2 MB\n    mov eax, 0x200000         ; 2 MB\n    mul ecx                    ; EAX = ECX × 2 MB\n    \n    ; Set flags: P (bit 0) + RW (bit 1) + PS (bit 7, huge page)\n    or  eax, 0x83             ; 0x83 = 0b10000011 = P + RW + PS\n    \n    ; Store in PD table\n    mov [pd_table + ecx*8], eax     ; Each entry is 8 bytes\n    mov dword [pd_table + ecx*8 + 4], 0  ; Upper 32 bits = 0\n    \n    inc ecx\n    cmp ecx, 2048              ; 512 entries × 4 tables = 2048 total\n    jl  .fill_pd\n    \n    ; ─────────────────────────────────────────────────────────────────────\n    ; STEP 5: Set EFER.LME (Long Mode Enable) to activate 64-bit mode\n    ; ─────────────────────────────────────────────────────────────────────\n    ; EFER is the Extended Feature Enable Register (MSR 0xC0000080).\n    ; Bit 8 (LME) enables long mode.\n    ; Bit 11 (NXE) enables no-execute bit (optional but useful).\n    \n    mov ecx, 0xC0000080       ; ECX = EFER MSR number\n    rdmsr                     ; Read MSR: EAX:EDX = MSR[ECX]\n    or  eax, 1 << 8           ; Set bit 8 (LME = Long Mode Enable)\n    wrmsr                     ; Write MSR back\n    \n    ; ─────────────────────────────────────────────────────────────────────\n    ; STEP 6: Enable paging (CR0.PG) → long mode becomes active\n    ; ─────────────────────────────────────────────────────────────────────\n    ; We've set up page tables (CR3), enabled PAE (CR4.PAE),\n    ; and enabled long mode (EFER.LME). Now enable paging to activate it.\n    \n    mov eax, cr0\n    or  eax, 1 << 31          ; CR0.PG = 1 (enable paging)\n    or  eax, 1 << 0           ; CR0.PE = 1 (already set by GRUB, but ensure it)\n    mov cr0, eax\n    \n    ; At this point, the CPU is in \"compatibility mode\" (32-bit code, 64-bit capable).\n    ; To switch to \"long mode\" (64-bit execution), we must far-jump.\n    \n    ; ─────────────────────────────────────────────────────────────────────\n    ; STEP 7: Load 64-bit GDT and far-jump to 64-bit code\n    ; ─────────────────────────────────────────────────────────────────────\n    ; The lgdt instruction loads the GDT pointer.\n    ; The far-jump (retf) reloads CS with the 64-bit code segment selector.\n    \n    lgdt [gdt64_ptr]          ; Load 64-bit GDT\n    \n    ; Far return: pop return address, push new CS, then retf to load CS\n    push 0x08                 ; Push code segment selector (offset of .code = 8)\n    mov eax, .start64         ; EAX = label address in 32-bit space\n    push eax                  ; Push 32-bit return address (will be 64-bit'd)\n    retf                      ; Far return: pops CS and RIP, loads new CS\n    \n    ; ╔═════════════════════════════════════════════════════════════════════╗\n    ; ║ FROM HERE ON: 64-BIT MODE (long mode)                              ║\n    ; ╚═════════════════════════════════════════════════════════════════════╝\n\nbits 64                    ; Assemble as 64-bit from here on\n\n.start64:\n    ; ─────────────────────────────────────────────────────────────────────\n    ; STEP 8: Reload data segment registers for 64-bit mode\n    ; ─────────────────────────────────────────────────────────────────────\n    ; In 64-bit mode, segment registers are mostly ignored (flat addressing).\n    ; However, some registers (like SS for stack) are still used for privilege checks.\n    ; We reload them to point to the 64-bit data segment (offset 0x10).\n    \n    mov ax, gdt64.data       ; AX = 0x10 (data segment selector)\n    mov ds, ax\n    mov es, ax\n    mov fs, ax\n    mov gs, ax\n    mov ss, ax               ; SS = data segment (for privilege level checks)\n    \n    ; ─────────────────────────────────────────────────────────────────────\n    ; STEP 9: Set up 64-bit kernel stack\n    ; ─────────────────────────────────────────────────────────────────────\n    ; We used a small temporary 32-bit stack (4 KB) to reach 64-bit mode.\n    ; Now switch to a large kernel stack (64 KB).\n    \n    mov rsp, stack_top       ; RSP = top of 64-bit kernel stack\n    \n    ; ─────────────────────────────────────────────────────────────────────\n    ; STEP 10: Enable SSE2 (Streaming SIMD Extensions)\n    ; ─────────────────────────────────────────────────────────────────────\n    ; Modern C code (especially with optimizations) may use SSE2 instructions.\n    ; SSE2 is disabled by default; we must enable it.\n    ; CR0.EM = 0 (emulation off), CR0.MP = 1 (monitor coprocessor on)\n    ; CR4.OSFXSR = 1 (OS supports FXSave/FXRestore)\n    ; CR4.OSXMMEXCPT = 1 (OS supports XMM exceptions)\n    \n    mov rax, cr0\n    and rax, ~(1 << 2)       ; Clear EM (emulation) bit\n    or  rax, 1 << 1          ; Set MP (monitor coprocessor) bit\n    mov cr0, rax\n    \n    mov rax, cr4\n    or  rax, 0x600           ; Set OSFXSR (bit 9) and OSXMMEXCPT (bit 10)\n    mov cr4, rax\n    \n    fninit                   ; Initialize FPU/MMX unit\n    \n    ; ─────────────────────────────────────────────────────────────────────\n    ; STEP 11: Pass Multiboot info to kmain()\n    ; ─────────────────────────────────────────────────────────────────────\n    ; x86_64 calling convention (System V AMD64 ABI):\n    ;   RDI = 1st argument (magic)\n    ;   RSI = 2nd argument (mbi pointer)\n    ;   RDX, RCX, R8, R9 = 3rd–6th arguments\n    ; \n    ; We saved magic and MBI in 32-bit .data section.\n    ; Load them and zero-extend to 64-bit registers.\n    \n    xor rdi, rdi             ; Clear RDI (will be 64-bit)\n    xor rsi, rsi             ; Clear RSI\n    mov edi, dword [saved_magic]  ; EDI = saved magic (zero-extends to RDI)\n    mov esi, dword [saved_mbi]    ; ESI = saved MBI (zero-extends to RSI)\n    \n    ; ─────────────────────────────────────────────────────────────────────\n    ; STEP 12: Call kmain() (kernel main in C)\n    ; ─────────────────────────────────────────────────────────────────────\n    call kmain\n    \n    ; If kmain() returns (shouldn't happen), halt the CPU\n    cli                      ; Disable interrupts\n    hlt                      ; Halt\n    jmp $                    ; Infinite loop\n\n; =============================================================================\n; 64-BIT KERNEL FUNCTIONS (called from C code later)\n; =============================================================================\n\n; ─────────────────────────────────────────────────────────────────────\n; gdt_flush(struct gdt_ptr *gdtp)\n; Reload the GDT after kernel initializes its own (more complete) GDT.\n; RDI = pointer to GDT pointer structure (uint16_t limit, uint64_t base)\n; ─────────────────────────────────────────────────────────────────────\ngdt_flush:\n    lgdt [rdi]               ; Load GDT from address in RDI\n    \n    ; Far jump to reload CS with new code segment selector\n    mov ax, 0x10             ; Data segment selector (index 2 × 8 = 0x10)\n    mov ds, ax\n    mov es, ax\n    mov fs, ax\n    mov gs, ax\n    mov ss, ax\n    \n    pop rax                  ; Pop return address\n    push qword 0x08          ; Push code segment selector\n    push rax                 ; Push return address\n    retfq                    ; Far return (loads new CS)\n\n; ─────────────────────────────────────────────────────────────────────\n; idt_load(struct idt_ptr *idtp)\n; Load the Interrupt Descriptor Table (set up later in kernel.c)\n; RDI = pointer to IDT pointer structure\n; ─────────────────────────────────────────────────────────────────────\nidt_load:\n    lidt [rdi]\n    ret\n\n; ─────────────────────────────────────────────────────────────────────\n; vmm_load_pml4(uint64_t pml4_addr)\n; Load new PML4 address into CR3 (for virtual memory later)\n; RDI = physical address of new PML4 table\n; ─────────────────────────────────────────────────────────────────────\nvmm_load_pml4:\n    mov cr3, rdi\n    ret\n\n; ─────────────────────────────────────────────────────────────────────\n; read_cr2() → uint64_t\n; Read CR2 (contains faulting address on page fault)\n; Returns in RAX\n; ─────────────────────────────────────────────────────────────────────\nread_cr2:\n    mov rax, cr2\n    ret\n\n; ─────────────────────────────────────────────────────────────────────\n; invlpg_addr(uint64_t vaddr)\n; Invalidate TLB entry for a virtual address (for VM updates)\n; RDI = virtual address to invalidate\n; ─────────────────────────────────────────────────────────────────────\ninvlpg_addr:\n    invlpg [rdi]\n    ret\n\n; =============================================================================\n; EARLY BOOT DATA (32-bit section, used during transition)\n; =============================================================================\nbits 32\nsection .data\n\nsaved_magic: dd 0           ; Storage for Multiboot magic number\nsaved_mbi:   dd 0           ; Storage for Multiboot info pointer\n\n; =============================================================================\n; EARLY BOOT PAGE TABLES (4 KB aligned, placed in BSS)\n; These are minimal 4-level page tables for identity mapping during bootstrap.\n; Later, kmain() calls vmm_init() to build more fine-grained tables.\n; =============================================================================\nsection .bss\n\nalign 4096\npml4_table: resb 4096      ; Page Map Level 4 (512 entries × 8 bytes)\npdpt_table: resb 4096      ; Page Directory Pointer Table\npd_table:   resb 4096      ; Page Directory (covers 0 – 1 GB)\npd_table2:  resb 4096      ; Page Directory (covers 1 – 2 GB)\npd_table3:  resb 4096      ; Page Directory (covers 2 – 3 GB)\npd_table4:  resb 4096      ; Page Directory (covers 3 – 4 GB)\n\n; 32-bit bootstrap stack (small, only used during transition)\nalign 16\nstack32_bottom: resb 4096\nstack32_top:                ; Stack top (grows downward)\n\n; Final 64-bit kernel stack (64 KB, large enough for kernel work)\nalign 16\nstack_bottom: resb 65536\nstack_top:                   ; Stack top for 64-bit kernel\n```\n\n### Educational Breakdown: The 12-Step Transition\n\n**Why save Multiboot registers first?** GRUB puts critical info in EAX/EBX. Any subsequent code might overwrite these registers. By saving them immediately, we preserve the Multiboot info for later use in `kmain()`.\n\n**Why PAE before long mode?** 64-bit long mode *requires* 4-level paging, which requires PAE. Without PAE, the CPU can only use 2-level paging (32-bit). Setting PAE unlocks the capability to use 4-level tables.\n\n**Why huge pages (2 MB) initially?** Huge pages simplify bootstrap: 512 entries × 2 MB = 1 GB per page directory. To map 4 GB requires only 4 PD tables. If we used 4 KB pages, we'd need thousands of page tables—unnecessarily complex.\n\n**Why far-jump?** The `retf` (far return) is the only way to reload CS (code segment register) without using privileged `ljmp` instructions. By pushing a new CS and return address, then executing `retf`, we force the CPU to load the new CS, which switches to 64-bit mode.\n\n**Why reload data segments in 64-bit mode?** In 64-bit mode, segment bases and limits are ignored (flat addressing). However, some segments (like SS) are still checked for privilege level during certain instructions. Reloading ensures consistency.\n\n**Why SSE2?** Modern GCC assumes SSE2 is available and may emit SSE2 instructions (`movapd`, `addsd`, etc.) for optimized code. Without enabling SSE2, these instructions will cause undefined-operation exceptions.\n\n---\n\n## 4. Kernel Entry (kmain)\n\nOnce the bootloader successfully transitions to 64-bit mode and calls `kmain()`, the kernel takes over.\n\n```c\n// src/core/kernel.c\n#include \"pmm.h\"\n#include \"vmm.h\"\n#include \"gdt.h\"\n#include \"idt.h\"\n#include \"screen.h\"\n#include \"task.h\"\n#include \"timer.h\"\n\nvoid kmain(uint32_t magic, multiboot_info_t* mbd) {\n    // ─────────────────────────────────────────────────────────────────────\n    // STEP 1: Initialize GDT (Global Descriptor Table)\n    // ─────────────────────────────────────────────────────────────────────\n    // The bootloader provided a minimal temporary GDT.\n    // Now we initialize a full GDT with kernel and user mode segments.\n    // This MUST be done before we set up virtual memory (which requires\n    // switching page tables, which requires a valid GDT).\n    \n    init_gdt();\n    \n    // ─────────────────────────────────────────────────────────────────────\n    // STEP 2: Initialize Physical Memory Manager (PMM)\n    // ─────────────────────────────────────────────────────────────────────\n    // Parse the Multiboot memory map to discover available RAM.\n    // Build a bitmap tracking which physical pages are in use.\n    // Mark kernel memory and loaded modules as reserved.\n    // This must be done early because:\n    //   - vmm_init() needs pmm_alloc_block() to allocate page tables\n    //   - We need to know how much memory is available\n    \n    pmm_init(magic, mbd);\n    \n    // ─────────────────────────────────────────────────────────────────────\n    // STEP 3: Initialize Interrupt Descriptor Table (IDT)\n    // ─────────────────────────────────────────────────────────────────────\n    // Set up IDT entries for exceptions (divide by zero, page fault, etc.)\n    // and hardware interrupts (timer, keyboard, etc.).\n    // This must be done before enabling interrupts.\n    \n    init_idt();\n    \n    // ─────────────────────────────────────────────────────────────────────\n    // STEP 4: Initialize Programmable Interval Timer (PIT)\n    // ─────────────────────────────────────────────────────────────────────\n    // Set up timer interrupt at 100 Hz (10 ms per tick).\n    // This is Every memory access goes through the GDT. Without a valid GDT, even simple operations can fault.\n\n**Why PMM before VMM?** The VMM needs to allocate page tables. Only the PMM can provide physical memory blocks. So PMM must initialize first.\n\n**Why IDT before timer?** If a timer interrupt fires before the IDT is set up, the CPU doesn't know where to find the handler and triple-faults. Setup IDT early.\n\n**Why timer before interrupts (STI)?** The PIT starts generating interrupts once initialized. If we don't configure the timer handler before enabling interrupts (STI), the first timer interrupt will crash the kernel.\n\n**Why STI before shell task?** The shell needs interrupts to handle user input (keyboard interrupts) and timer-driven scheduling. Enable interrupts just before creating the shell.\n\n---\n\n## 5. Common Boot Issues & Debugging\n\n### Issue: Kernel Crashes Immediately\n\n**Cause**: Invalid page table or GDT entry\n\n**Debug**:\n```bash\n# Enable QEMU monitor to inspect CPU state\nqemu-system-x86_64 -cdrom jarvis.iso -monitor stdio\n(qemu) info registers  # Check CR3, CR0, GDT, IDT\n```\n\n### Issue: Bootloader Doesn't Recognize Kernel\n\n**Cause**: Multiboot2 header not in first 32 KB or checksum wrong\n\n**Debug**:\n```bash\n# Check binary structure\nobjdump -h kernel.elf | head -20\nreadelf -S kernel.elf | grep multiboot\n\n# Verify header offset\nnm -S kernel.elf | grep loader\n```\n\n### Issue: GRUB Loads Kernel But It Doesn't Boot\n\n**Cause**: Long mode transition failed (PAE not set, EFER.LME not set, paging not enabled)\n\n**Solution**: Add serial logging to loader.s:\n```assembly\n; After each major step, write to serial port 0x3F8\nmov al, 'P'             ; Print 'P' for PAE\nmov dx, 0x3F8          ; Serial port\nout dx, al\n```\n\nThen capture output:\n```bash\nqemu-system-x86_64 -cdrom jarvis.iso -serial file:debug.log\n# Then cat debug.log\n```\n\n---\n\n## ✅ Summary\n\nIn this phase, you learned:\n\n✅ Multiboot2 header specification and magic number validation  \n✅ How GRUB passes CPU control to your kernel  \n✅ The 12-step process to transition from 32-bit to 64-bit mode  \n✅ Physical Address Extension (PAE) and its requirement for long mode  \n✅ 4-level page table creation with huge pages  \n✅ EFER.LME activation and long mode entry  \n✅ Kernel entry point (kmain) and initialization sequence  \n✅ Stack setup and CPU register initialization  \n✅ Debugging boot issues  \n\n**Next**: [Phase 3: Memory Management](./03-memory-management.md) – Learn how the kernel builds detailed virtual memory maps and manages physical/virtual address translation.\n\n---\n\n**Exercises**:\n1.
